# Requirements Document

## Introduction

ฟีเจอร์นี้คือการสร้าง **เว็บบล็อกแบบ Static (Static Blog Website)** สำหรับเผยแพร่บทสรุปกฎหมาย/กฎระเบียบด้านเทคโนโลยีสารสนเทศของไทย โดยเว็บไซต์จะแสดง "1 กฎหมาย = 1 บทความ" อ่านข้อมูลจากไฟล์ JSON ที่สร้างจากโฟลเดอร์ผลลัพธ์รายกฎหมายของ Pipeline v5.0 (`claude_schedule_prompts.txt`) ซึ่งปัจจุบันสร้างไฟล์ต่อกฎหมายไว้ 4 รูปแบบ ได้แก่ เอกสาร Word สรุปและเปรียบเทียบ (`.docx`), ภาพอินโฟกราฟิก 9:16 (`.png`), ผังความสัมพันธ์ (`.png`) และเนื้อหาโพสต์โซเชียล (`.txt`)

ขอบเขตงานครอบคลุม 2 ส่วนหลัก:
1. **เว็บไซต์ Static** — `index.html` + ไฟล์ JavaScript + ไฟล์ CSS + สคีมาข้อมูล JSON + เวิร์กโฟลว์เผยแพร่ผ่าน GitHub Pages + สคริปต์อัปเดต Manifest (แบบ add-only) โครงสร้างอ้างอิงจาก repo `ai-news` และ `gov-news-thailand`
2. **การปรับปรุงพรอมป์ Pipeline** — แก้ไข `claude_schedule_prompts.txt` ให้สร้างไฟล์ข้อมูล JSON และคัดลอกเข้าโฟลเดอร์ข้อมูลของเว็บไซต์โดยอัตโนมัติ เพื่อให้การรันตามกำหนดเวลา (Scheduled Run) เผยแพร่กฎหมายใหม่รายวันได้ง่าย

เนื้อหาและชื่อกฎหมายทั้งหมดที่แสดงต่อผู้ใช้เป็น **ภาษาไทย 100%** และต้องรองรับการแสดงผลฟอนต์ไทย (รูปแบบ THSarabun ตามตัวอย่างอ้างอิง)

## Glossary

- **Blog_Site (เว็บบล็อก)**: เว็บแอปพลิเคชันแบบ Static ฝั่งไคลเอนต์ ที่โหลดข้อมูล JSON แล้วเรนเดอร์เป็นบทความ ประกอบด้วย `index.html`, ไฟล์ JavaScript และ CSS
- **Law_Post (บทความกฎหมาย)**: หน่วยเนื้อหา 1 บทความ ซึ่งแทนกฎหมาย 1 ฉบับ
- **Law_Folder (โฟลเดอร์รายกฎหมาย)**: โฟลเดอร์ผลลัพธ์ต่อกฎหมาย 1 ฉบับ เช่น `28-09-2026/01_พรบ.อำนวยความสะดวกฯ_2569/` ที่มีไฟล์ `.docx`, `.png`, `.mmd`, `.txt`
- **Data_Ingestor (ตัวแปลงข้อมูลเข้า)**: ส่วนประมวลผล (สคริปต์) ที่อ่าน Law_Folder แปลงเนื้อหา `.docx`, ฝังภาพ `.png`, และดึงข้อความ `.txt` เพื่อสร้าง Post_JSON
- **Post_JSON (ข้อมูลบทความ)**: ไฟล์ข้อมูล JSON ต่อรอบวันที่ ที่บรรจุอาร์เรย์ `posts` สำหรับให้ Blog_Site เรนเดอร์
- **Manifest (แฟ้มสารบัญ)**: ไฟล์ `manifest.json` ที่รวมรายการรอบวันที่/บทความทั้งหมด ใช้แบบ **add-only** (เพิ่มเท่านั้น ไม่ลบ ไม่เขียนทับ)
- **Manifest_Updater (ตัวปรับปรุงสารบัญ)**: สคริปต์ `update-manifest.py` ที่อัปเดต Manifest แบบ add-only
- **Listing_View (หน้ารายการ)**: หน้าแสดงรายการบทความทั้งหมด
- **Post_View (หน้าบทความเดี่ยว)**: หน้าแสดงเนื้อหาบทความ 1 ฉบับ
- **Pipeline (ไปป์ไลน์)**: Skill v5.0 ใน `claude_schedule_prompts.txt` ที่ตรวจจับและแปรรูปกฎหมายไอที
- **Publish_Workflow (เวิร์กโฟลว์เผยแพร่)**: GitHub Actions workflow ที่เผยแพร่ Blog_Site ผ่าน GitHub Pages
- **Announcement_Date (วันที่ประกาศ)**: วันที่กฎหมายถูกประกาศ/เผยแพร่ในราชกิจจานุเบกษาหรือแหล่งทางการ
- **THSarabun_Font (ฟอนต์ไทยสารบรรณ)**: ชุดฟอนต์ไทยที่ใช้แสดงผลให้ไม่กลายเป็นกล่องสี่เหลี่ยม

## Requirements

### Requirement 1: การแปลงข้อมูลจากโฟลเดอร์รายกฎหมาย (Data Ingestion)

**User Story:** As a ผู้ดูแลเนื้อหา, I want ให้ระบบแปลงเนื้อหาจากโฟลเดอร์รายกฎหมายเป็นข้อมูลบทความโดยอัตโนมัติ, so that ไม่ต้องคัดลอกเนื้อหาด้วยมือ

#### Acceptance Criteria

1. WHEN Data_Ingestor พบ Law_Folder ที่มีไฟล์ `1_เอกสารสรุปและเปรียบเทียบข้อกฎหมาย.docx`, THE Data_Ingestor SHALL แปลงเนื้อหาของไฟล์ `.docx` เป็นข้อความ HTML และบันทึกลงในฟิลด์เนื้อหาหลักของ Post_JSON โดยสร้าง Post_JSON หนึ่งรายการต่อหนึ่ง Law_Folder
2. WHEN Data_Ingestor พบไฟล์ `2_ภาพอินโฟกราฟิก_แนวตั้ง_9ต่อ16.png` ใน Law_Folder, THE Data_Ingestor SHALL บันทึกเส้นทางอ้างอิงของภาพอินโฟกราฟิกลงในฟิลด์ภาพของ Post_JSON
3. IF Law_Folder มีไฟล์ `.docx` เนื้อหาหลักแต่ไม่มีไฟล์ `2_ภาพอินโฟกราฟิก_แนวตั้ง_9ต่อ16.png`, THEN THE Data_Ingestor SHALL กำหนดฟิลด์ภาพอินโฟกราฟิกของ Post_JSON เป็นค่าว่าง และดำเนินการแปลงเนื้อหาส่วนที่เหลือต่อไปโดยไม่หยุดทำงาน
4. WHEN Data_Ingestor พบไฟล์ `4_แผนผังความสัมพันธ์กฎหมายและบุคคล.png` ใน Law_Folder, THE Data_Ingestor SHALL บันทึกเส้นทางอ้างอิงของภาพผังความสัมพันธ์ลงในฟิลด์ภาพของ Post_JSON
5. IF Law_Folder มีไฟล์ `.docx` เนื้อหาหลักแต่ไม่มีไฟล์ `4_แผนผังความสัมพันธ์กฎหมายและบุคคล.png`, THEN THE Data_Ingestor SHALL กำหนดฟิลด์ภาพผังความสัมพันธ์ของ Post_JSON เป็นค่าว่าง และดำเนินการแปลงเนื้อหาส่วนที่เหลือต่อไปโดยไม่หยุดทำงาน
6. WHEN Data_Ingestor พบไฟล์ `3_เนื้อหาโพสต์เฟซบุ๊ก_โซเชียลมีเดีย.txt` ใน Law_Folder, THE Data_Ingestor SHALL ดึงข้อความทั้งหมดจากไฟล์ `.txt` และบันทึกลงในฟิลด์ความเห็น (comments) ของ Post_JSON
7. IF Law_Folder มีไฟล์ `.docx` เนื้อหาหลักแต่ไม่มีไฟล์ `3_เนื้อหาโพสต์เฟซบุ๊ก_โซเชียลมีเดีย.txt`, THEN THE Data_Ingestor SHALL กำหนดฟิลด์ความเห็น (comments) ของ Post_JSON เป็นค่าว่าง และดำเนินการแปลงเนื้อหาส่วนที่เหลือต่อไปโดยไม่หยุดทำงาน
8. IF Law_Folder ไม่มีไฟล์ `.docx` เนื้อหาหลัก, THEN THE Data_Ingestor SHALL ข้าม Law_Folder นั้นโดยไม่สร้าง Post_JSON และบันทึกข้อความแจ้งเตือนที่ระบุชื่อโฟลเดอร์ที่ถูกข้ามและสาเหตุว่าไม่พบไฟล์เนื้อหาหลัก
9. IF Data_Ingestor ไม่สามารถอ่านหรือแปลงไฟล์ `.docx` เนื้อหาหลักได้ (ไฟล์เสียหายหรือเปิดไม่ได้), THEN THE Data_Ingestor SHALL ข้าม Law_Folder นั้นโดยไม่สร้าง Post_JSON บันทึกข้อความแจ้งเตือนที่ระบุชื่อโฟลเดอร์และสาเหตุของความล้มเหลว และดำเนินการประมวลผล Law_Folder ถัดไปต่อไป
10. THE Data_Ingestor SHALL กำหนดชื่อบทความของ Law_Post จากชื่อของ Law_Folder เป็นภาษาไทย โดยตัดเลขลำดับนำหน้าและเครื่องหมายขีดล่างเริ่มต้นออก (เช่น จากโฟลเดอร์ `07_ระเบียบคณะกรรมการนโยบายศูนย์ข้อมูล_2569` เป็นชื่อบทความ `ระเบียบคณะกรรมการนโยบายศูนย์ข้อมูล_2569`)

### Requirement 2: สคีมาข้อมูล Post_JSON และ Manifest

**User Story:** As a นักพัฒนาเว็บ, I want สคีมาข้อมูล JSON ที่ชัดเจนและสม่ำเสมอ, so that Blog_Site เรนเดอร์บทความได้ถูกต้องทุกฟิลด์

#### Acceptance Criteria

1. THE Post_JSON SHALL บรรจุอาร์เรย์ `posts` โดยแต่ละสมาชิกมีฟิลด์ที่จำเป็นครบทุกฟิลด์ ได้แก่ `id` (ข้อความ ยาว 1 ถึง 128 อักขระ ไม่ซ้ำกันภายในรอบวันที่เดียวกัน), `slug` (ข้อความ ยาว 1 ถึง 200 อักขระ), `title` (ข้อความ ยาว 1 ถึง 500 อักขระ), `announcement_date` (วันที่รูปแบบ ISO 8601 คือ YYYY-MM-DD), `content_html` (ข้อความ), `infographic_image` (ข้อความเส้นทางหรือ URL), `relationship_image` (ข้อความเส้นทางหรือ URL), `comments` (อาร์เรย์ ความยาว 0 ถึง 1,000 สมาชิก), `source_url` (ข้อความ), และ `tags` (อาร์เรย์ของข้อความ ความยาว 0 ถึง 50 สมาชิก)
2. THE Post_JSON SHALL บรรจุฟิลด์ระดับบนสุด `date` (รอบวันที่ รูปแบบ ISO 8601 คือ YYYY-MM-DD) และ `generated_at` (เวลาที่สร้างข้อมูล รูปแบบ ISO 8601 พร้อมโซนเวลา คือ YYYY-MM-DDThh:mm:ssZ)
3. THE Manifest SHALL บรรจุรายการรอบวันที่และบทความทั้งหมด โดยแต่ละรายการระบุ `date` (รอบวันที่ รูปแบบ ISO 8601 คือ YYYY-MM-DD) เป็นคีย์ และเส้นทางไปยังไฟล์ Post_JSON ของรอบวันที่นั้น
4. WHEN Manifest_Updater เพิ่มรายการใหม่, THE Manifest_Updater SHALL เพิ่มรายการแบบ add-only โดยไม่ลบหรือไม่เขียนทับรายการที่มีอยู่เดิม
5. IF Manifest_Updater พบรายการที่มี `id` ซ้ำกับรายการเดิมภายในรอบวันที่เดียวกัน, THEN THE Manifest_Updater SHALL คงรายการเดิมไว้ ไม่เพิ่มรายการซ้ำ และคงสถานะ Manifest เดิมไว้ไม่เปลี่ยนแปลง
6. THE Post_JSON และ Manifest SHALL เข้ารหัสด้วย UTF-8 เพื่อรองรับข้อความภาษาไทย
7. IF สมาชิกใน `posts` ขาดฟิลด์ที่จำเป็นตามข้อ 1 หรือฟิลด์ใดมีค่าว่าง หรือค่าฟิลด์ไม่ตรงรูปแบบที่กำหนด, THEN THE Post_JSON SHALL ถูกจัดเป็นข้อมูลไม่ผ่านการตรวจสอบ และแสดงข้อความแจ้งข้อผิดพลาดที่ระบุฟิลด์และสมาชิกที่ผิดพลาด โดยไม่บันทึกทับข้อมูลเดิม
8. IF Manifest_Updater ไม่สามารถอ่านหรือแยกวิเคราะห์ (parse) ไฟล์ Manifest ที่มีอยู่เดิมได้, THEN THE Manifest_Updater SHALL ยุติการเพิ่มรายการ คงไฟล์ Manifest เดิมไว้โดยไม่แก้ไข และแสดงข้อความแจ้งข้อผิดพลาดที่ระบุสาเหตุการอ่านไม่สำเร็จ

### Requirement 3: หน้ารายการบทความ (Blog Listing View)

**User Story:** As a ผู้อ่าน, I want เห็นรายการกฎหมายทั้งหมดพร้อมวันที่ประกาศ, so that เลือกอ่านกฎหมายที่สนใจได้

#### Acceptance Criteria

1. WHEN ผู้อ่านเปิด `index.html`, THE Blog_Site SHALL โหลด Manifest และ Post_JSON แล้วแสดง Listing_View ที่มีรายการ Law_Post ทั้งหมดจาก Manifest ภายใน 3 วินาที
2. THE Listing_View SHALL แสดงชื่อกฎหมาย (`title`) และ Announcement_Date ของแต่ละ Law_Post โดยแสดง Announcement_Date ในรูปแบบ วัน/เดือน/ปี พ.ศ.
3. WHILE Listing_View แสดงรายการ Law_Post, THE Blog_Site SHALL เรียงลำดับจาก Announcement_Date ล่าสุดไปเก่าสุด และเมื่อวันที่ประกาศเท่ากันให้เรียงตามชื่อกฎหมายแบบพจนานุกรมไทย
4. WHEN ผู้อ่านเลือก Law_Post หนึ่งรายการใน Listing_View, THE Blog_Site SHALL แสดง Post_View ของบทความนั้นภายใน 2 วินาที
5. IF การโหลด Manifest หรือ Post_JSON ล้มเหลว, THEN THE Blog_Site SHALL แสดงข้อความแจ้งข้อผิดพลาดเป็นภาษาไทยที่ระบุสาเหตุและมีช่องทางให้ลองใหม่ แทนหน้าว่างเปล่า
6. IF Manifest ไม่มี Law_Post ใดเลย, THEN THE Blog_Site SHALL แสดงข้อความภาษาไทยแจ้งว่ายังไม่มีบทความ แทนหน้าว่างเปล่า

### Requirement 4: หน้าบทความเดี่ยว (Single Post View)

**User Story:** As a ผู้อ่าน, I want อ่านเนื้อหาสรุปกฎหมาย พร้อมภาพและความเห็นในหน้าเดียว, so that เข้าใจกฎหมายฉบับนั้นครบถ้วน

#### Acceptance Criteria

1. WHEN Blog_Site แสดง Post_View, THE Blog_Site SHALL แสดงชื่อกฎหมายและ Announcement_Date (รูปแบบ วัน/เดือน/ปี พ.ศ.) ที่ส่วนหัวของบทความ
2. WHEN Blog_Site แสดง Post_View, THE Blog_Site SHALL แสดงองค์ประกอบตามลำดับ ส่วนหัว → เนื้อหาหลัก (`content_html` ที่แปลงจากเอกสารสรุปและเปรียบเทียบ) → ภาพประกอบ → ส่วนความเห็น
3. WHEN Blog_Site แสดง Post_View, THE Blog_Site SHALL แสดงภาพอินโฟกราฟิก 9:16 และภาพผังความสัมพันธ์ภายในเนื้อหาบทความ พร้อมข้อความ alt ภาษาไทยกำกับภาพทั้งสอง
4. WHEN Blog_Site แสดง Post_View, THE Post_View SHALL แสดงเนื้อหาความเห็น (จากไฟล์ `.txt`) ในส่วน "ความเห็น" ที่อยู่ล่างสุดของบทความ ถัดจากภาพประกอบทั้งหมด
5. IF Law_Post ใดไม่มีภาพอินโฟกราฟิกหรือภาพผังความสัมพันธ์, THEN THE Post_View SHALL แสดงเนื้อหาส่วนที่เหลือได้โดยไม่แสดงกรอบภาพว่าง ไอคอนภาพเสีย หรือช่องว่างแทนภาพที่ขาดหาย
6. IF Law_Post ใดไม่มีเนื้อหาความเห็นหรือความเห็นว่างเปล่า, THEN THE Post_View SHALL ไม่แสดงส่วน "ความเห็น" และแสดงเนื้อหาส่วนที่เหลือได้ตามปกติ

### Requirement 5: การแสดงผลภาษาไทยและฟอนต์ (Thai Language & Font Handling)

**User Story:** As a ผู้อ่าน, I want ข้อความภาษาไทยแสดงผลถูกต้อง, so that อ่านได้โดยไม่เป็นกล่องสี่เหลี่ยมหรืออักขระเพี้ยน

#### Acceptance Criteria

1. THE Blog_Site SHALL กำหนดแอตทริบิวต์ `lang="th"` บนองค์ประกอบ root ของเอกสาร และประกาศการเข้ารหัสอักขระเป็น UTF-8 ในส่วนหัวของเอกสาร HTML ทุกหน้า
2. WHEN ผู้อ่านเปิดหน้าใด ๆ ของเว็บไซต์, THE Blog_Site SHALL โหลดและใช้ THSarabun_Font ผ่านกฎ `@font-face` เพื่อแสดงผลข้อความภาษาไทยทั้งหมดในเนื้อหาหลัก
3. IF THSarabun_Font ไม่สามารถโหลดได้สำเร็จภายใน 3 วินาที, THEN THE Blog_Site SHALL แสดงข้อความภาษาไทยด้วยฟอนต์ไทยสำรอง (fallback) ที่รองรับอักขระไทยครบทุกตัว (พยัญชนะ สระ วรรณยุกต์ และเครื่องหมาย) โดยยังคงแสดงเนื้อหาได้ครบถ้วนไม่มีอักขระที่แสดงเป็นกล่องสี่เหลี่ยม (tofu)
4. THE Blog_Site SHALL แสดงชื่อกฎหมาย เนื้อหาบทความ และความเห็นทั้งหมดเป็นภาษาไทย โดยอักขระภาษาไทยทุกตัวที่แสดงผลต้องตรงกับข้อมูลต้นฉบับ ไม่มีอักขระเพี้ยน (mojibake) หรือสระ/วรรณยุกต์ที่ลอยผิดตำแหน่ง
5. IF ข้อความมีการผสมภาษาไทยกับตัวเลขอารบิกหรืออักขระละติน, THEN THE Blog_Site SHALL แสดงผลอักขระทุกชุดในบรรทัดเดียวกันโดยไม่ตัดคำผิดตำแหน่งและไม่มีอักขระใดแสดงเป็นกล่องสี่เหลี่ยม

### Requirement 6: การเผยแพร่ผ่าน GitHub Pages (Publishing Workflow)

**User Story:** As a ผู้ดูแลระบบ, I want เผยแพร่เว็บไซต์ผ่าน GitHub Pages, so that ผู้อื่นเข้าถึงเว็บได้ผ่านอินเทอร์เน็ต

#### Acceptance Criteria

1. THE Blog_Site SHALL มีไฟล์ `.nojekyll` ที่ราก repository เพื่อปิดการประมวลผลด้วย Jekyll
2. THE Publish_Workflow SHALL อยู่ในไดเรกทอรี `.github/workflows/` และกำหนดค่าให้ทริกเกอร์เมื่อมีการ push ไปยัง branch เผยแพร่ที่กำหนด (branch `main`) และเผยแพร่เนื้อหาผ่าน GitHub Pages
3. WHEN มีการ push ไปยัง branch `main`, THE Publish_Workflow SHALL เผยแพร่ `index.html` พร้อมไฟล์ JavaScript, CSS, ข้อมูล JSON และภาพทั้งหมดที่อ้างอิงจาก `index.html` ให้เข้าถึงได้แบบสาธารณะภายใน 10 นาทีนับจากเวลาที่ workflow เริ่มทำงาน
4. THE Blog_Site SHALL ใช้เส้นทางอ้างอิงไฟล์แบบสัมพัทธ์ (relative path) สำหรับทุกไฟล์ JavaScript, CSS, ข้อมูล JSON และภาพ เพื่อให้ทำงานได้ภายใต้ path ย่อยของ GitHub Pages
5. WHEN การเผยแพร่ผ่าน Publish_Workflow เสร็จสมบูรณ์, THE Publish_Workflow SHALL ทำให้ `index.html` เข้าถึงได้ผ่าน URL สาธารณะของ GitHub Pages โดยได้รับผลตอบกลับที่แสดงว่าหน้าเว็บพร้อมใช้งาน (สถานะสำเร็จ)
6. IF ไฟล์ที่ `index.html` อ้างอิง (JavaScript, CSS, ข้อมูล JSON หรือภาพ) ไม่พบในระหว่างการเผยแพร่, THEN THE Publish_Workflow SHALL หยุดการเผยแพร่ ไม่ทับการเผยแพร่เดิมที่ใช้งานได้อยู่ และรายงานข้อความแสดงข้อผิดพลาดที่ระบุไฟล์ที่หายไป ในบันทึกการทำงานของ GitHub Actions
7. IF การเผยแพร่ผ่าน Publish_Workflow ล้มเหลว, THEN THE Publish_Workflow SHALL รายงานสถานะความล้มเหลวในบันทึกการทำงานของ GitHub Actions และคงการเผยแพร่ครั้งล่าสุดที่สำเร็จไว้โดยไม่เปลี่ยนแปลง

### Requirement 7: การอัปเดตรายวันอัตโนมัติผ่าน Pipeline (Daily Update Automation)

**User Story:** As a ผู้ดูแลเนื้อหา, I want ให้ Pipeline สร้างข้อมูล JSON และผสานเข้ากับเว็บไซต์อัตโนมัติในการรันรายวัน, so that เผยแพร่กฎหมายใหม่ทุกวันได้โดยไม่ต้องแก้ด้วยมือ

#### Acceptance Criteria

1. WHEN Pipeline ประมวลผลกฎหมายไอทีใหม่ในการรันรายวันจนได้ข้อมูลครบทุกฟิลด์บังคับ, THE Pipeline SHALL สร้างไฟล์ Post_JSON ของรอบวันที่นั้นให้ผ่านการตรวจความถูกต้องตามสคีมาใน Requirement 2 (ทุกฟิลด์บังคับมีค่าและชนิดข้อมูลตรงตามสคีมา)
2. IF ข้อมูลกฎหมายไอทีใหม่ไม่ผ่านการตรวจความถูกต้องตามสคีมาใน Requirement 2, THEN THE Pipeline SHALL ไม่สร้างไฟล์ Post_JSON ของรายการนั้น และบันทึกข้อความแสดงข้อผิดพลาดที่ระบุฟิลด์ที่ไม่ผ่าน โดยไม่หยุดการประมวลผลรายการอื่นในรอบเดียวกัน
3. WHEN Pipeline สร้าง Post_JSON ของรอบวันเสร็จ, THE Pipeline SHALL คัดลอกไฟล์ Post_JSON และภาพที่เกี่ยวข้องทั้งหมดเข้าไปยังโฟลเดอร์ข้อมูลของ Blog_Site (เช่น `data/`) โดยไฟล์ปลายทางต้องมีเนื้อหาตรงกับไฟล์ต้นทางทุกไบต์
4. IF การคัดลอกไฟล์ Post_JSON หรือภาพเข้าโฟลเดอร์ข้อมูลของ Blog_Site ล้มเหลว หรือไฟล์ปลายทางไม่ตรงกับต้นทาง, THEN THE Pipeline SHALL ไม่เรียก Manifest_Updater ในรอบนั้น คงไฟล์ข้อมูลเดิมของ Blog_Site ไว้โดยไม่แก้ไข และบันทึกข้อความแสดงข้อผิดพลาดที่ระบุไฟล์ที่ล้มเหลว
5. WHEN Pipeline คัดลอกข้อมูลเข้าโฟลเดอร์ข้อมูลของ Blog_Site สำเร็จครบทุกไฟล์, THE Pipeline SHALL เรียก Manifest_Updater เพื่อเพิ่มเฉพาะรายการใหม่แบบ add-only โดยไม่แก้ไขและไม่ลบรายการที่มีอยู่เดิม และไม่เพิ่มรายการที่มีตัวระบุซ้ำกับรายการเดิม
6. IF Manifest_Updater ทำงานล้มเหลว, THEN THE Pipeline SHALL คงไฟล์ Manifest เดิมไว้โดยไม่แก้ไข และบันทึกข้อความแสดงข้อผิดพลาดที่ระบุสาเหตุการล้มเหลว
7. IF Pipeline ตรวจไม่พบกฎหมายไอทีใหม่ในรอบการรัน (จำนวนรายการใหม่เท่ากับ 0), THEN THE Pipeline SHALL ไม่สร้างหรือแก้ไขไฟล์ข้อมูลของ Blog_Site จบการทำงานของรอบนั้นด้วยสถานะสำเร็จ และบันทึกข้อความว่าไม่มีรายการใหม่
8. THE พรอมป์ใน `claude_schedule_prompts.txt` SHALL ระบุขั้นตอนสำหรับการรันรายวันครบทั้งสามขั้นตอนตามลำดับ ได้แก่ การสร้าง Post_JSON, การคัดลอกข้อมูล, และการเรียก Manifest_Updater
9. THE Pipeline SHALL ตั้งชื่อโฟลเดอร์และไฟล์ผลลัพธ์รายกฎหมายเป็นภาษาไทยทั้งหมด โดยไม่ปรากฏอักษรภาษาอังกฤษในส่วนชื่อกฎหมาย ตามกฎเดิมของ Skill

### Requirement 8: โครงสร้างโปรเจกต์เว็บไซต์ (Site Project Structure)

**User Story:** As a นักพัฒนาเว็บ, I want โครงสร้างไฟล์ที่ชัดเจนตามรูปแบบ repo อ้างอิง, so that ดูแลรักษาและต่อยอดได้ง่าย

#### Acceptance Criteria

1. THE Blog_Site SHALL แยกไฟล์ตามหน้าที่เป็นสามองค์ประกอบที่แยกจากกันชัดเจน ได้แก่ `index.html` (โครงหน้า), ไดเรกทอรี JavaScript สำหรับตรรกะการเรนเดอร์, และไดเรกทอรี CSS สำหรับสไตล์
2. THE Blog_Site SHALL เก็บไฟล์ข้อมูล JSON (Post_JSON และ Manifest) ไว้ในไดเรกทอรีข้อมูล `data/` เท่านั้น
3. THE Blog_Site SHALL มีสคริปต์ Manifest_Updater (`update-manifest.py`) ที่รากโปรเจกต์
4. WHEN Manifest_Updater ทำงาน, THE Manifest_Updater SHALL ปรับปรุง Manifest แบบ add-only โดยคงรายการที่มีอยู่เดิมไว้ทั้งหมด
5. IF Manifest_Updater ไม่พบไฟล์ Post_JSON ที่จะเพิ่มหรืออ่านไฟล์นั้นไม่ได้, THEN THE Manifest_Updater SHALL ไม่แก้ไข Manifest และแสดงข้อความแจ้งข้อผิดพลาดที่ระบุไฟล์ที่มีปัญหา
6. WHEN เบราว์เซอร์โหลด `index.html`, THE Blog_Site SHALL โหลดและเรนเดอร์บทความจากไฟล์ข้อมูล JSON ฝั่งไคลเอนต์ล้วนโดยไม่ต้อง build ฝั่งเซิร์ฟเวอร์
7. IF การโหลดหรือแยกวิเคราะห์ไฟล์ข้อมูล JSON ล้มเหลว, THEN THE Blog_Site SHALL แสดงข้อความแจ้งข้อผิดพลาดเป็นภาษาไทยแทนหน้าว่างเปล่า
